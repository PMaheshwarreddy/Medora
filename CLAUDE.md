# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Medora is a hospital kiosk web app: a patient talks to "Dr. Medora" (voice) or fills in a form, a smart band supplies vitals, the patient reviews what was collected, and the backend produces a pre-consultation triage report that can be downloaded or sent by SMS/email. The company's back office is the app's home (`/`): dashboard, a Kiosk section, clients (tenants) with their one key, feature switches and the API calls made with that key, sessions, activity logs, and the medical knowledge database. There are deliberately no Team, System or separate API-access pages (the user removed them on 2026-10-13); their backend endpoints still exist. The patient kiosk lives under `/#/kiosk` and can be opened from the back office as any client (a preview).

`medora_master_blueprint.md` is the original product plan. Where it disagrees with the code, the code reflects later decisions: English and Malayalam (added 2026-10-19), no thermal slip (PDF + SMS/email instead), no manual vitals entry, features configurable per client, Supabase only (no local database), the form flow working offline on a local medical model (voice online only), and a CrewAI specialist panel followed by a reviewed report writer.

## Models and stack

The user presents this to their manager; keep it current when a model or major library changes.

| Model | Where | Used for |
| :--- | :--- | :--- |
| Gemini 3.1 Flash Live preview (`gemini_live_model`, voice "Kore") | `voice.py` | The real-time voice conversation and its tool calls |
| Gemini 2.5 Flash (`gemini_text_model`) | `llm.GeminiLlm`, panel chair | Symptom understanding, panel chair, report writer, safety reviewer, condition check, precautions, vitals decision, ingestion planner |
| Gemini 3.1 Flash-Lite (`gemini_panel_model`) | `panel.py` | Each specialist agent (up to 5 in parallel) |
| all-MiniLM via local Ollama (`ollama_embed_model`) | `knowledge_base.Embedder` | Embeddings for meaning-based symptom matching (RAG) |
| MedGemma 4B via local Ollama (`offline_model`) | `llm.make_offline_llm`, `panel.LocalPanel` | The whole report (specialists, chair, writer, reviewer, checks, precautions) when there is no internet; 27B needs a GPU machine |
| Qwen 2.5 3B via local Ollama (`ollama_model`) | `llm.OllamaLlm` | Fallback summary only when Gemini fails and no medical model is available; never conditions or medicines |

Agents: CrewAI 1.15 (18 specialist profiles, a chair who is a general physician). Backend: Python 3.12, FastAPI, Uvicorn, Pydantic 2, SQLAlchemy 2, psycopg 3, google-genai, numpy, ReportLab (PDF); Twilio (SMS) and SMTP (email) wired but unconfigured. Database: PostgreSQL on Supabase (Mumbai). Frontend: Flutter 3.44 Web, Riverpod 3, go_router, hand-written Web Audio, Web Bluetooth for the QC Wireless band. Tooling: uv, pytest, flutter test. A report makes about 11 model calls and takes about 30 s; the Gemini key is free tier, so production needs a paid key.

## Commands

Backend (`backend/`, Python 3.12, managed with `uv`):

```bash
./run_dev.sh                      # starts the API on :8100 (against Supabase)
uv run pytest -q                  # all tests (SQLite, no Docker or network needed)
uv run pytest tests/test_api.py::test_health -q   # one test
```

Frontend (`frontend/`, Flutter Web):

```bash
./run_dev.sh                      # back office at /, kiosk at /#/kiosk (wraps `flutter run -d chrome`)
flutter analyze
dart format lib test
flutter test                      # all tests
flutter test test/voice_test.dart --plain-name "barge-in"   # one test
flutter build web --dart-define=MEDORA_API=https://api.example.com
```

- Phones (phone intake, report QR codes) cannot reach `localhost`. `frontend/run_dev.sh` serves the debug app on 0.0.0.0:8090 (Chrome here opens it as localhost) with `MEDORA_PUBLIC_URL=http://<LAN IP>:8090`, so its QR codes work from phones on the same Wi-Fi (the QR once pointed at `localhost:56790`, a random dev port, and phones were refused). `frontend/run_lan.sh` builds the app with `MEDORA_PUBLIC_URL=http://<LAN IP>:8080` and serves it on 0.0.0.0:8080; open the kiosk at `http://localhost:8080/#/kiosk` (the microphone needs localhost or https), phones open the LAN address from the QR. Without `MEDORA_API` the app calls port 8100 on the host it was opened from (`api_client.medoraApiBase`), and `backend/run_dev.sh` listens on 0.0.0.0 (`MEDORA_HOST=127.0.0.1` to keep it local). The firewall must allow 8080 and 8100.

- Plain `flutter run -d chrome` fails with "Failed to launch browser" from a terminal inside the VS Code snap: the snap's GSettings paths make Chrome abort. `frontend/run_dev.sh` launches Chrome through `tool/chrome.sh`, which restores the system environment.
- The API listens on **8100**, not 8000: another service on the dev machine owns 8000. The frontend default (`medoraApiBase` in `lib/api/api_client.dart`) matches.
- `run_dev.sh` still starts a local `medora-db` Postgres container if `MEDORA_DATABASE_URL` ever points at localhost, but there is no local database any more: see below.
- `backend/.env` (gitignored) holds `MEDORA_DATABASE_URL`, which is the team's **Supabase** database: the only database. On 2026-10-17 the user chose Supabase only ("don't use the local db"): the local Postgres container and its data volume were removed after every record was verified in Supabase, and `MEDORA_CLOUD_DATABASE_URL` (the old mirror target) is empty. Do not reintroduce a local database. `.env.example` lists every setting. The `python -m app.ingest` CLI also targets `MEDORA_DATABASE_URL`, so back-office uploads and CLI loads go straight into Supabase.
- API docs are served at `http://localhost:8100/docs`.

## Architecture

API-first: the FastAPI backend is the product; the kiosk and back office are both clients of it, and so can a customer's own system be.

### Backend (`backend/app/`)

- `main.py` `create_app(settings)` is an app factory. The engine, text LLM, voice providers, ingestion pipeline and live runtime state live on `app.state` (`engine`, `llm`, `offline_llm`, `offline_panel`, `offline`, `voice_provider`, `offline_voice_provider`, `ingest`, `runtime`); tests swap these directly instead of patching, and pass `background_tasks=False`.
- Offline (decided 2026-10-18): the form flow works without internet, voice does not. `background.py` probes for internet every 10 s (`runtime.online`); `/api/status` reports it, and the kiosk's welcome screen then disables voice and keeps "Type my details". The report then runs on the local medical model (`offline_model`, MedGemma 4B via Ollama: `llm.make_offline_llm`, `panel.LocalPanel`) through the SAME pipeline, prompts, review and code rules, with `offline_panel_size` (0 since 2026-10-28: the chair alone; each specialist is another 2-3 minute call) and stored precautions without a model choosing (`build_report(lean=True)`, `precautions.choose(select=False)`), because the development laptop (i7-1355U, no GPU) reads about 20 tokens/s and writes about 7 with MedGemma 4B; `OllamaLlm` calls take turns (a lock per model, 900 s each: queued calls used to time out inside Ollama) and use `ollama_threads` (10, twice the default speed); each answer is capped (`llm.MAX_ANSWER_TOKENS` 1800, and `answer_tokens` per call: 600-700 for the understanding, condition check and review, 1500 for the chair; at 1100 its answer was cut off) because in JSON mode MedGemma once wrote on until the 15-minute timeout and the review was lost; and the local model fills in fixed forms (Ollama structured output, `schema=`: `panel.CHAIR_FORM`/`SPECIALIST_FORM`, `report_writer.FIT_FORM`/`REVIEW_FORM`; hosted models ignore it), after which the review answered in 57 s and the chair in 133 s with valid JSON and offline reports show reviewed medicines again (the review is strict: it refused cetirizine for a viral fever); the case carries fewer, shorter passages (`triage.LEAN_*`). Measured on 2026-10-29 on that laptop: understanding 3 min, chair 5, condition check 3.5, writer 6.7 (the full report about 20 minutes), so the kiosk's report request waits up to 30 min and a repeated request joins the running one (`reports.py` `report_tasks`). A GPU machine is what makes offline reports quick; the patient's page (`/final`) and PDF are served from memory offline. There is still NO local database (the user refused one on 2026-10-18): `offline.py` keeps in memory only the clients, API keys and back-office sign-ins seen online, the offline visits with their reports, and queued activity-log lines, and `background.py` copies visits, reports and log lines into Supabase when the internet is back. Consequences to keep in mind: the server must be started online (schema check, knowledge index, kiosk keys), and a server restart while offline loses visits not yet copied. The knowledge index (`knowledge_base.py`) holds disease details, medicines and precautions in memory too, so the search works offline. Code that touches the database on a kiosk path must catch `offline.UNREACHABLE` and fall back to memory; `db.make_engine` sets a 5 s connect timeout so that happens quickly. The mirror code in `background.py` (to `MEDORA_CLOUD_DATABASE_URL`) is idle because that setting is empty. Phone intake works offline too (2026-10-28, the user asked for the typed flow to work without internet): the phone reaches the kiosk server over the hospital Wi-Fi, so a hand-off opened while the database is unreachable lives in `offline.handoffs` for its 30 minutes, and the welcome page's phone tile stays on. Offline visits get no "visited before?" lookup; `offline.flush` links each copied visit to the record with the same phone and name (`patients.same_person`), else a new one. The web app must not load anything from the internet: both run scripts pass `--no-web-resources-cdn` (CanvasKit served locally; Google's fallback fonts are fetched only for glyphs our fonts lack), and find the LAN address from `hostname -I` when there is no route to 1.1.1.1. The guideline search offline needs the snapshot (`python -m app.kb snapshot`, own connection without the 8 s limit); without it the report runs without guideline passages.
- Multi-tenancy (`tenancy.py`): a `Tenant` is a client. `deps.current_tenant` resolves the client in this order: a signed-in back-office user previewing a client (session token + `X-Tenant-Id`), a client's own system (`X-Api-Key`), a kiosk (`X-Kiosk-Key`, or `?key=` on the voice WebSocket), else the default client. Requests made with an API key are written to `api_request_logs` by the middleware in `main.py`; routes that do not need the client still take the `note_api_key` dependency so the call is validated and logged. `system_settings` holds what the back office may change at runtime (currently the panel size). A client has ONE key (`mk_...`): `routers/admin._issue_client_key` registers the kiosk key as an `ApiKey` row too, so the same value works as `X-Kiosk-Key`, in the kiosk link, and as `X-Api-Key` (logged); issuing a new key revokes the old one everywhere. Only a hash of the key is stored. `/api/config` returns the calling kiosk's own switches; sessions carry `tenant_id`. `tenancy.record()` writes the activity log shown in the back office; call it for anything an operator would want to see, but never for what a hospital's own people do (doctors signing, hospital staff accounts): that goes only to the hospital's audit log (`hospital.service.audit`), for privacy (user's rule of 2026-10-28). Old lines of that kind (`tenancy.HOSPITAL_EVENTS`) are filtered out of `/api/admin/logs` and the overview.
- JSON is camelCase on the wire and snake_case in Python via `schemas.ApiModel`. Exceptions: the report body is a plain dict written with camelCase keys in `triage.py`, and `IntakeSession.vitals` is stored with snake_case keys.
- Auth: kiosk endpoints take the optional kiosk key (`Kiosk` dependency). Back-office endpoints (`routers/admin.py`, `routers/knowledge_admin.py`) use the `Admin` dependency: a signed-in user (`auth.py`, `routers/auth.py`). Accounts are email + password (scrypt hashes); signing in returns a session token that the app sends in the `X-Admin-Key` header (the name is historical; `Authorization: Bearer` works too) and keeps in `localStorage`. Registration is open and every new account works at once (there is no Team page); with `MEDORA_REGISTRATION_OPEN=false` only the first account does and later ones need `PATCH /api/admin/users/{id}`. There is no shared admin key any more (`MEDORA_ADMIN_KEY` in an old `.env` is ignored). Backend tests seed a session whose token is `test-key` (`_seed_admin`). Report endpoints are guarded only by the unguessable session id.
- The app's own tables (`models.py`) are created at startup by `tenancy.ensure_schema`. There are no migrations: a column added to an existing table must also be listed in `_ADDED_COLUMNS` there, or older databases (including the cloud mirror) will not get it.
- Hospital portal (2026-10-22, step 1 of the manager's plan): a hospital's own back office, kept apart from the company back office at the user's request ("separate folder, don't mix"). Backend `app/hospital/` (`models.py`, `service.py`, `router.py`, routes `/api/hospital/...`); frontend `lib/hospital/` (shell, login, own API client and widgets, `pages/`), route `/#/hospital`. Hospital people have their OWN accounts and sessions (`hospital_users`, `hospital_sessions`, token in `X-Hospital-Token`, browser key `medora.hospitalSession`), never the company's `admin_users`: a hospital login gets 401 on `/api/admin`, and the company's open registration cannot create one. Roles: `hospital_admin` (the only role with this portal), `doctor` (needs a registration number; portal not built yet), `staff`. The company creates a hospital's first admin in "Add client (hospital)" (name, email and a password the company chooses; `TenantCreate.admin_*`, created in the same transaction as the client) and more later with the "Hospital portal" button on a client card (`/api/admin/tenants/{id}/hospital-admins`, `lib/admin/hospital_admins_dialog.dart`; password optional). A password the company chose works as is; a temporary one (shown once) must be changed at first sign-in (`must_change_password`). Every hospital query is scoped to `user.tenant_id`, never a tenant from the request; another hospital's visit is a 404. Pages: dashboard (today in the hospital's time zone), doctors, staff, departments (each may take a report department from `panel.DEPARTMENTS`, for the doctor queue later), visits and reports (opening one writes `visit.viewed` to `hospital_audit`), audit log and kiosk activity, settings (name, address, logo as a data URL up to 300 KB, time zone; for report letterheads later). Switching a hospital (tenant) off closes its portal. Tests: `tests/test_hospital.py`, `test/hospital_test.dart`.
- The full flow (2026-10-22, the manager's plan, steps 2-6; Health Connect not built): patient records, doctor report, doctor portal, signed final report, phone intake.
  - Patients (`app/patients/`): one `Patient` per person per hospital, matched by phone digits; the kiosk's "Have you visited before?" (`POST /api/intake/patients`, or `/api/handoffs/{code}/phone/patients` from a phone) returns only masked names ("A*** R***") and ages; a picked `patientId` links the visit, otherwise a new record is made, and reported allergies/conditions/daily medicines/operations/weight are merged (`attach`). History reaches the report AI only as `history_text` (doctor-confirmed diagnoses and prescriptions, plus what the patient reported before) and the doctor portal (`timeline`); never the kiosk screen. The form has a fourth step "Your health" (conditions chips, daily medicines, past operations, weight, required under 12); voice asks long-term conditions, daily medicines and a child's weight.
  - Doctor review switch per client (`Tenant.doctor_review`, default on, "Doctor review" on the client card): the report is then `awaitingDoctor` and `routers/reports.for_patient` strips the AI's clinical fields from the top level of every patient-facing response and PDF, but its `patientView` shows the possible conditions and the doctor's reviewed medicines under "the doctor decides" (since 2026-10-28, the user's rule; before that it was preliminary, with none); `doctorView` (unfiltered by `sensitive.py`: the doctor sees pregnancy etc.) is never sent to the patient, with or without review. The kiosk report shows the visit number (session id's first 6 characters, upper case), "a doctor will see you", and a QR to the patient's page `/#/r/<visit>`.
  - Doctor report (in the stored report's `doctorView`): every condition with an AI `probability` (chair's number, made consistent by `triage.with_probabilities`: ≤100 in total, never above an earlier one), the ones the `_FIT` check doubted kept with `doubtReason` (`report_writer.Kept.reasons`), and `doctor_medicines`: the reviewed list plus injections, weight-based children's doses (only with a weight) and emergency first-line care, each `doctorOnly`; controlled drugs and allergies are still refused, nothing without the pharmacist review. The patient-side `_rules` are unchanged.
  - Doctor portal: backend `app/doctor/` (`/api/doctor/...`: queue for the doctor's department or all, last 24 h, emergencies first; `pick` locks the visit to one doctor (409 for others, stale after 3 h); visit (Medora's doctor view, told, vitals, record, history, draft; audited); draft; `finalize` (needs a diagnosis, each medicine a dose and frequency) builds `DoctorReview.final_report` via `patient_view` from the doctor's decisions only (doses never reworded), with doctor (name, qualification, registration number) and hospital letterhead; private notes never leave the portal); frontend `lib/doctor/` at `/#/doctor` (own sign-in key `medora.doctorSession`; login screens take a `PortalSession`). Look (2026-10-28): dark pine sidebar with the doctor's card on wide screens (top bar below 980 px), greeting, figure tiles, patient cards with initials and urgency stripe, a patient banner with an allergy alert, vitals as tiles; shared pieces in `lib/doctor/doctor_widgets.dart`. The signed report's language is the doctor's choice (`ReportLanguageToggle`, key `report-language`, English by default; `Draft.language`, `doctor/router._InLanguage`), not the visit's. The AI report is never edited; `DoctorReview` sits beside it. Patient side: `GET /api/sessions/{id}/final` (status preparing/waiting/in_consultation/final/no_review, and the final report) and `/final.pdf` (`report_pdf.render_final_pdf`, bilingual, letterhead and logo, signature block).
  - Phone intake (`app/handoff/`, the manager's infection concern): the welcome page's second tile is "Use my phone" (`/kiosk/phone`, a QR to `/#/phone/<code>`; 30-minute random code is the only access); the phone fills the same `IntakeForm` (with visited-before) and sends it; the kiosk polls, takes vitals if needed, saves the visit itself (`mode: phone`, review screen auto-saves) and tells the phone, which then links to `/#/r/<visit>`. "No phone? Type on this screen" stays (offline, or no phone); nurses can scan the QR on their own device. QR links use `--dart-define=MEDORA_PUBLIC_URL` (else the kiosk's own address, which phones cannot reach if it is localhost). Patient pages live in `lib/patient/`; the bilingual report pieces are shared in `widgets/patient_report.dart`.
  - Tests: `tests/test_doctor.py`, `test/new_flow_test.dart`.
- The medical knowledge tables (`diseases`, `symptoms`, `drugs`, `disease_links`, `precautions`) and the ingestion bookkeeping (`ingestion_runs`, `ingestion_rejects`) live in `knowledge_models.py` on a separate `KnowledgeBase`. They are never created at startup, only by `python -m app.ingest init-db`, which refuses to touch knowledge tables in an older layout unless `--replace-legacy` is given and they are empty.

Report pipeline (`routers/reports.py` → `triage.py`), five steps:

1. Symptom understanding and screening: one model call turns the patient's words into symptom terms (a clinical term and a plain wording for each) and screens the case against the whole specialist roster, listing only the specialties it concerns.
2. Evidence (`knowledge_base.py`, no model): each symptom is matched to knowledge-base symptom rows by name, alias, spelling variant and embedding similarity (local Ollama `all-minilm`, vectors cached in `data/rag_cache/`); candidate diseases are scored by how much of the presentation they explain, weighting rare symptoms higher. Several rows matched for one complaint count once (`SymptomMatch.group`).
3. Specialist panel (`panel.py`, CrewAI on Gemini): the standard roster is 18 specialties, specialists only (`SPECIALISTS`, each with its scope, what it must never miss and what is not its field; these profiles are the agents' prompts). On 2026-10-18 the user removed Family Medicine, Internal Medicine and Emergency Medicine as agents ("not specialists"; emergency is a department): do not add generalist agents back. General medicine (viral fever, cold, and dengue, malaria and typhoid for India) is the chair's job; the report's `department` is one of `DEPARTMENTS` = the roster plus "General OPD" and "Emergency Department" (`triage._department`: an emergency always goes to the Emergency Department, anything unknown to General OPD). `choose_panel` asks Pediatrics for children, then the screened specialties up to the panel-size limit (default 5), skipping ones that cannot apply (OB/GYN for men, Pediatrics for adults); the list may be empty (a plain fever concerns no specialty), and then the chair concludes alone. Each specialist is its own one-agent crew, run concurrently; one who answers `relevant: false` has stepped aside: the chair never sees that opinion, and the report credits it with nothing and lists it as "stepped aside". If everyone steps aside the chair concludes alone; a specialist whose call fails is left out; the panel fails only if every call failed. The agents' instructions (`SPECIALIST_OUTPUT`, `CHAIR_OUTPUT`) were tuned against live cases on 2026-10-18: a symptom every field shares (fever, tiredness, aches) does not make a case a specialist's, but a main complaint their field lists does; common conditions in India first; never a condition whose defining features are absent. Re-run live cases after changing them. Specialists run on the faster `gemini_panel_model`, the chair on `gemini_text_model`.
   Precautions (`precautions.py`) are chosen after the panel: stored precautions for the likely conditions come first, but a model only selects which suit this patient (it may not reword them); if fewer than three suit, new ones are written, filtered by rules in code, and reviewed by a second model pass. Unreviewed written lines are never shown. For urgent and emergency cases stored precautions are not offered at all (they are prevention advice), and an emergency always starts with a fixed "tell the staff now" line. `precautionsSource` records which path was taken. These add two model calls to a report.
4. Report writer (`report_writer.py`), after the panel: a writer model drafts the clinical summary, medicines WITH dose, frequency, duration, maximum daily amount and cautions (knowledge-base medicines preferred, otherwise standard first-line treatment); a condition that needs a test before treatment (malaria, dengue, typhoid, TB) gets symptom relief only, with the test in the doctor notes, and fills missing lifestyle advice and doctor notes; a separate reviewer model ("clinical pharmacist") may only approve or reject each medicine, each written condition and the summary; a third, focused pass (`_FIT`) checks every condition, the panel's included, against what the patient reported: a condition other than the most likely one stays only if the model can name a feature of the case pointing to it more than to the likely one (a shared symptom such as fever does not count) or a red flag that makes it a must-rule-out; dropped ones are kept in `conditionsRuledOut`. The panel chair is told never to list a condition for its knowledge-base score. Then rules in code: no medicines under age 12 or in an emergency, no controlled drugs or injections, a dose must look like a dose, prescription drugs are marked, a pregnancy check for women 12-50, a warning when the patient already took that medicine, and if the review fails no written medicine or summary is shown. Medicines carry `source` (knowledge_base | suggested). If the panel fails while online, one model triages and the writer also names conditions, under the same review. The local Ollama model is never allowed to write conditions or medicines (`_local`/`_hosted`). Gemini calls retry on 429/503 (`llm.with_retries`), and every hosted call has a limit of `llm.CALL_TIMEOUT` (120 s, both in `with_retries` and the client's `HttpOptions`; CrewAI's Gemini provider takes it through `client_params`, it ignores a plain `timeout`): a stuck connection once held a report for 1 h 47 min. A call that times out is tried once more. For speed, `llm.json(..., thinking=N)` caps Gemini 2.5's reasoning (0 for symptom understanding, 512 for checks and precautions, 1024 for chair, writer and reviewer; the chair's default thinking alone took 20 s), and independent calls run side by side: condition check with the writer's draft, then the review with precautions. A typical report takes about 30 s and about 11 model calls.
   Vitals (`vitals.py`) are judged against fixed normal ranges in code (normal / low / high; heart rate and blood pressure not judged under 18) and shown in the report and PDF as `vitalsAssessment`.
5. Safety and grounding, in code: vitals set a minimum urgency that nothing can lower; a relevant specialist calling an emergency keeps urgency at least "urgent"; patient advice that names a medicine is dropped; the patient's name and contact details never enter the case text.

Progress (`progress.py`): `build_report` records each stage, the specialists asked and each one's answer in an in-memory `ReportProgress` (`app.state.progress`); `GET /api/sessions/{id}/report/progress` serves it and the kiosk's waiting screen (`widgets/panel_orbit.dart`) polls it to animate the panel. The screen shows only what that endpoint reports; keep it that way.

Which models may write conditions and medicines is one flag, `llm.clinical()`: Gemini and the configured offline medical model (`OllamaLlm(..., clinical=True)`) may, under the same review and rules; the small general model (`ollama_model`, Qwen 2.5 3B) may not. When only that small model answers (online with Gemini down, or offline with no `offline_model`) it writes only the summary and the report carries NO possible conditions or medicines, with a note saying why: it was wrong too often to show. Keep that rule. Vitals are never waived offline (`/api/intake/vitals-check` answers "needed"). (Online with the panel failing is different: see step 4.) CrewAI telemetry is disabled in `panel.py` before the import; it must stay off because cases are patient data. Reports are generated once per session and then served from `triage_reports`; older stored reports lack the newer keys, so readers use defaults.

Knowledge ingestion (`app/ingest/`, run with `python -m app.ingest ...` against `MEDORA_DATABASE_URL`): an ETL pipeline where the AI plans and code executes. Source files are arbitrary and badly named, so nothing trusts file names.

- `sniff` detects the format from content (csv, json, obo, OBO-style owl, and xml, where each repeated element under the root becomes one JSON-like record: children by tag, a list when repeated, attributes as `@name`; streamed, so MeSH's 313 MB is fine) and builds a sample; a plan may use `[0]` on a listed path to take the first item only; `planner` asks Gemini for a declarative `Plan` (`plan.py`: which columns/JSON paths feed which table, or a verdict of junk / not data); `transform` applies the plan to every record with deterministic cleaning and validation into a `Staged` object; `load` writes that in one transaction. Free-text articles skip the planner: `articles.py` has the model extract facts, and drops any name that does not occur in the article.
- Flow per file: `plan` → human review (`show`, `revise "<instruction>"`, `reject`, `approve`) → `load` → optionally `undo`. Planning never writes knowledge rows. `status` lists every run. The back office's Database tab drives the same pipeline over `/api/admin/knowledge/...` (upload = store + plan).
- Cleaning rules in `transform.py` that the search depends on: `"Name (ABBR)"` becomes the name plus an alias; a "disease" with more than `MAX_SYMPTOMS_PER_DISEASE` symptoms in one file is a reversed row and is dropped with the symptoms only it used; aliases claimed by several rows are dropped.
- Invariants worth keeping: loads are idempotent (match on `normalized_name`, then aliases; text is fill-if-empty); a load above `MAX_REJECT_RATE` fails rather than loading a wrong mapping; `enrich_only` outputs never create rows and never match through ambiguous synonyms; model output is cached by file hash in `data/ingest_cache/`, so the same reviewed plan is reused against another database without new model calls.
- The planner model is inconsistent between runs (it has mapped package sizes to dosage and set an ontology to create 20,000 symptoms). The review flags and the validation gates exist for that; do not remove them in favour of trusting the plan.
- Gemini free-tier limits are per key, not per process: run one `plan` at a time, or calls collide and crawl through retries.
- `medora_datasets /` (note the trailing space in the folder name) holds the source files.

New knowledge base (`app/kb/`, 2026-10-27; run with `python -m app.kb init|load <key>...|all|link|embed|status` against `MEDORA_KNOWLEDGE_DATABASE_URL`, a SEPARATE Supabase project, Singapore, knowledge only; clients and visits stay in `MEDORA_DATABASE_URL`). ## Conventions specific to this repo

- Clinical safety rules in `triage.py` and `report_writer.py` (vital thresholds, urgency can only be raised, the medicine rules above, no medicine names in patient advice) are intentional. The user chose on 2026-10-12 to show possible conditions and medicines in the report, labelled as for the doctor to confirm, and on 2026-10-15 to show doses and let the AI suggest medicines the knowledge base lacks, provided they are reviewed; never weaken the review or the code rules to get more medicines shown. The thresholds are provisional adult cut-offs awaiting clinician review.
- Pregnancy and sexual-health wording (`app/sensitive.py`, applied to every report in `triage._report`): the user decided on 2026-10-18 that the report must never name pregnancy, ectopic pregnancy, STIs, PID, condoms and the like on the AI's initiative; conditions, advice, notes and sentences naming them are dropped unless the patient raised the topic. The clinically necessary step stays for the doctor in neutral words: `DOCTOR_CHECK` (LMP and urine hCG) for women 12-50 with lower-abdominal, pelvic or period complaints, and "Doctor to check LMP / hCG" on medicines not in `_SAFE_IN_PREGNANCY`. Do not remove that doctor check: a missed ectopic pregnancy can kill.
- Medicines (2026-10-18, after "no proper medicine suggestions"): the writer is told the usual first-visit symptom relief (paracetamol, cetirizine, dextromethorphan, antacid/pantoprazole, ORS, topical diclofenac) and Indian brand names for "medication already taken" (`report_writer._BRANDS` in code too, e.g. Dolo = paracetamol); continuing a medicine already taken is approved when the caution counts those doses. Fever under three days without localising signs is "Viral fever"; typhoid, malaria, dengue and hepatitis need their own features; "emergency" needs a red flag present in the case.
- The patient's report (screen and PDF) does not show the specialist panel's discussion, who raised which condition, or which parts an AI wrote (no "AI-suggested" labels); the user decided this on 2026-10-17. The data stays in the stored report, and the disclaimer that it is an automated summary for the doctor to confirm stays.
- Back office client switches (`clients_tab.dart`) flip at once and save in the background, reverting with a message on failure; they are never disabled, because a disabled "on" switch looked off. Switching off the last intake mode is refused with an explanation. The theme draws off switches with an outline so they do not look disabled.
- The waiting screen's orbit shows the specialists asked; when none were (a case no specialty owns) it says the case is being reviewed.
- During the voice agent's vitals step the microphone is closed (`VoiceController._takeVitals`) and reopened when the vitals are sent.
- Verification scripts, scripted voice providers and seeded test data belong in tests or a scratch directory, never in `app/` or `lib/`.
